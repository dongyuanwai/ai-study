# 《从调用模型到构建 Agent》系列大纲

> 副标题：前端工程师的 LangChain.js 与 LangGraph 核心原理与工程实践

## 1. 系列定位

这不是一套 LangChain.js 或 LangGraph API 手册，而是一套解释 Agent 系统为什么这样设计、如何逐步失控、又如何重新获得控制的工程教程。

系列主线：

> 从一次不可控的模型调用出发，逐步构建一个可约束、可恢复、可观测、可评估的 Agent 系统。

系列主要回答四类问题：

1. **原理**：模型、消息、工具、Agent 和 Graph 之间是什么关系？
2. **设计**：哪些决策交给模型，哪些必须留在确定性代码中？
3. **工程**：如何处理状态、循环、失败、恢复、人工审批和前端交互？
4. **边界**：什么时候不需要 Agent，什么时候不需要 LangGraph？

## 2. 目标读者

- 熟悉 TypeScript、异步编程和常见前端工程实践；
- 调用过 LLM API，或做过简单聊天应用；
- 学过 LangChain.js、LangGraph，但知识仍然停留在零散 API；
- 希望理解 Agent 的运行机制与生产级工程问题。

读者不需要具备机器学习或 Python 背景。

## 3. 阅读完成后的能力目标

读完整个系列后，读者应该能够：

- 说清 LangChain.js、LangGraph、LangSmith 与模型服务的职责边界；
- 手写并解释一个最小 Agent Loop；
- 为复杂任务选择 Chain、Agent、Workflow 或 Graph；
- 正确设计 State、Node、Edge 与 Reducer；
- 区分上下文、短期记忆、长期记忆和 Checkpoint；
- 为工具调用加入校验、权限、超时、重试和人工审批；
- 将流式运行事件转换成可理解的前端 UI 状态；
- 从结果、过程、成本和安全多个维度测试与评估 Agent。

## 4. 贯穿案例：AI 技术文章研究助手

全系列只维护一个主案例，并随着文章逐步增强：

```text
输入技术主题
→ 澄清读者与写作目标
→ 生成结构化大纲
→ 调用工具检索资料
→ 并行研究各章节
→ 汇总研究结果
→ 生成文章初稿
→ 评价并修改初稿
→ 人工确认
→ 输出最终文章
```

最终系统应具备：

- 结构化任务输入和文章大纲；
- 受约束的资料检索工具；
- 显式状态与可解释工作流；
- 并行研究和评价—优化循环；
- Thread 级持久化与中断恢复；
- 实时进度展示；
- 发布前人工审批；
- Trace、测试数据集和基础评估。

案例的演进遵循一个原则：每篇只增加一种关键能力，避免代码复杂度掩盖文章主题。

## 第 01 篇｜LangChain.js、LangGraph 与 Agent 到底是什么关系

### 核心命题

LangChain.js 提供构建 Agent 的通用组件和高层抽象，LangGraph 提供长时间、有状态工作流所需的运行时能力；Agent 则是建立在这些能力之上的一种控制循环。

### 要解决的问题

- 模型、Chain、Agent、Workflow、Graph 分别是什么？
- LangChain.js 和 LangGraph 是替代关系还是分层关系？
- `createAgent` 已经存在，为什么还需要理解 LangGraph？
- 什么场景只调用模型就够了？

### 内容结构

1. 从一张混乱的技术栈图开始；
2. 模型是推理组件，不是完整应用；
3. LangChain.js：消息、模型、工具、结构化输出与 Agent 抽象；
4. LangGraph：状态、控制流、持久化和恢复；
5. LangSmith：Trace、调试、评估与持续改进；
6. Chain、Workflow 与 Agent 的控制权差异；
7. 一张场景选择表：直接调用、Chain、Agent、Graph；
8. 介绍贯穿系列的文章研究助手。

### 示例产物

只画出系统边界和数据流，不急于构建复杂 Agent。

### 读者带走

能够根据问题复杂度选择抽象层，而不是默认给所有 LLM 应用套上 Agent。

## 第 02 篇｜LLM 应用为什么不是普通的函数调用

### 核心命题

传统程序的函数负责执行确定规则，LLM 调用产生的是概率性候选结果；可靠应用必须在模型外部建立约束和验证。

### 要解决的问题

- 为什么相同输入可能产生不同输出？
- Prompt 写得足够详细，能否保证正确？
- LLM 应用常见的失败类型有哪些？
- 确定性代码和概率性模型应该如何分工？

### 内容结构

1. `fetch()` 成功不等于业务成功；
2. 传输成功、格式正确、事实正确、任务完成是四件事；
3. 不确定性的来源：采样、歧义、上下文与外部知识；
4. LLM 应用的四层边界：输入、生成、验证、执行；
5. 用约束、重试、回退和人工确认管理失败；
6. “能由代码确定的事情，不交给模型猜”；
7. 成本、延迟和质量之间的权衡。

### 案例演进

实现最小文章选题分析器，记录它在格式、遗漏和一致性上的失败，形成后续改造基线。

### 读者带走

从“怎样让模型更聪明”转向“怎样让系统容纳模型的不确定性”。

---

## 第 03 篇｜Messages、Prompt 与上下文：模型究竟看到了什么

### 核心命题

模型只根据当前请求中的上下文生成结果；消息历史、工具结果和检索资料都是被临时组装进上下文的数据，而不是模型天然拥有的记忆。

### 要解决的问题

- System、User、Assistant、Tool 消息如何组成协议？
- 对话历史为什么不等于记忆？
- Prompt 与 Context Engineering 有什么区别？
- 上下文是不是越多越好？

### 内容结构

1. 从“模型为什么忘了”这个误解切入；
2. Message 不只是字符串，而是带角色和结构的协议；
3. 工具调用与 Tool Message 的配对关系；
4. Prompt 是上下文的一部分，不是上下文的全部；
5. 上下文选择、排序、压缩和隔离；
6. 无关上下文如何干扰模型判断；
7. 上下文窗口、消息历史、短期记忆的边界；
8. 设计一个可检查的 Context Builder。

### 案例演进

为研究助手增加明确的消息模型和上下文构建层，显示每次请求实际发送给模型的内容。

### 读者带走

能够把上下文当作需要设计和调试的运行时输入，而不是不断追加的聊天记录。

---

## 第 04 篇｜结构化输出：连接概率模型与确定性程序

### 核心命题

结构化输出不是格式美化，而是概率模型与确定性程序之间的类型边界。

### 要解决的问题

- 为什么不应该用正则解析模型文本？
- Schema 能保证哪些事情，又不能保证哪些事情？
- 类型正确但语义错误怎么办？
- 验证失败后应该重试、修复还是降级？

### 内容结构

1. 文本适合人读，结构化数据适合程序消费；
2. Schema 的三重作用：描述、约束和运行时验证；
3. TypeScript 静态类型为什么不等于运行时安全；
4. 语法合法、结构合法和业务合法的区别；
5. 校验、重试、错误反馈和降级策略；
6. Schema 设计中的过度约束与约束不足；
7. 结构化输出的可测试性；
8. 何时应保留自由文本。

### 案例演进

使用 Zod 定义文章目标、大纲章节和研究任务，让后续节点消费稳定的数据结构。

### 读者带走

能够为模型输出建立可靠边界，并明确 Schema 不能替代事实校验。

## 第 05 篇｜Tool Calling：模型并没有真的调用函数

### 核心命题

模型只生成“想调用哪个工具以及参数是什么”的请求；真正的验证、授权、执行和结果回传由 Agent Runtime 完成。

### 要解决的问题

- Tool Calling 的完整协议是什么？
- 工具描述为什么会影响模型选择？
- 工具粒度应该大还是小？
- 如何处理越权、重复执行和工具异常？

### 内容结构

1. 拆开一次 Tool Calling 的完整时序；
2. 工具定义是模型看到的操作界面；
3. 名称、描述与参数 Schema 的设计；
4. 参数合法不代表操作安全；
5. 超时、重试、幂等性与错误分类；
6. 读工具和写工具的权限差异；
7. 工具返回内容的压缩与清洗；
8. Prompt Injection 为什么会穿过工具边界；
9. 哪些工具调用必须由人批准。

### 案例演进

为研究助手增加资料搜索和文档读取工具，并限制域名、结果数量、超时和返回长度。

### 读者带走

能够把 Tool 当成安全敏感的系统边界，而不是一个加了描述的普通函数。

## 第 06 篇｜Agent Loop：Agent 为什么能够自主行动

### 核心命题

Agent 的“自主性”来自一个由模型参与决策的观察—行动循环，而不是来自某个神秘的 Agent 对象。

### 要解决的问题

- 一个最小 Agent Loop 如何运行？
- 模型什么时候回答，什么时候调用工具？
- 循环如何终止，为什么会失控？
- Middleware 在 Agent 中解决什么问题？

### 内容结构

1. 手写最小 Agent Loop；
2. 观察、决策、行动、反馈四个阶段；
3. 模型选择工具与运行时执行工具的分工；
4. 停止条件、最大步数、超时与调用预算；
5. 重复调用、错误累积和上下文膨胀；
6. Middleware：在模型调用和工具调用周围加入横切能力；
7. 动态模型、上下文裁剪、重试与人工审批；
8. 什么时候固定工作流比 Agent Loop 更合适。

### 案例演进

把研究工具接入循环，使研究助手能够自主决定是否继续查找资料，同时加入步数和成本上限。

### 读者带走

能够不用框架名词解释 Agent，并能识别一个自主循环的风险边界。

## 第 07 篇｜为什么复杂 Agent 需要 Graph

### 核心命题

当应用出现分支、循环、并行、等待和恢复时，真正需要管理的已经不是调用顺序，而是状态随控制流发生的变化。

### 要解决的问题

- 顺序 Chain 为什么会逐渐难以维护？
- Graph 是流程图、状态机，还是运行时？
- 固定 Workflow 与动态 Agent 如何组合？
- Graph API 与 Functional API 应该怎么选？

### 内容结构

1. 从不断增长的 `if/else + while + Promise.all` 切入；
2. 节点是计算，边是控制流，状态是事实来源；
3. 显式 Graph 带来的可读性、可恢复性与可观测性；
4. 确定性节点和概率性节点可以共存；
5. Workflow、Agent 以及“Agent 作为节点”；
6. Graph API 与 Functional API 的思维差异；
7. 不需要 LangGraph 的场景；
8. 将研究助手画成第一张运行图。

### 案例演进

把文章生成流程从单个循环改造成包含规划、研究、写作和审核的显式工作流。

### 读者带走

能够从控制流复杂度，而不是从项目大小判断是否需要 LangGraph。

## 第 08 篇｜State、Node、Edge 与 Reducer：LangGraph 的核心模型

### 核心命题

LangGraph 最重要的不是 Graph 的形状，而是节点之间如何通过受约束的 State 进行协作。

### 要解决的问题

- State 应该保存什么，不应该保存什么？
- Node 为什么返回局部更新，而不是修改全局对象？
- Reducer 如何处理并行写入？
- 哪些条件应该成为代码中的 Edge？

### 内容结构

1. State 是一次运行的事实来源；
2. 输入、输出、内部状态和外部业务数据的边界；
3. Node 的职责：读取状态、执行单一计算、返回局部更新；
4. Edge 表达确定性控制流，模型决策只是其中一种输入；
5. 覆盖、追加、去重与自定义 Reducer；
6. 并行节点写入同一字段时发生什么；
7. State Schema 作为节点间契约；
8. 状态不变量与错误状态；
9. 大对象、派生数据和敏感数据为什么不宜全部进入 State。

### 案例演进

设计研究助手的 State Schema，并为资料列表、章节草稿和消息分别选择合并规则。

### 读者带走

能够先设计状态契约，再编写节点；能够解释 Reducer 为什么是并行工作流的基础设施。

---

## 第 09 篇｜分支、循环与并行：五种常见 Agent 工作流

### 核心命题

大多数复杂 Agent 都可以拆解为少数几种工作流模式；选择模式的关键是任务结构，而不是框架 API。

### 要解决的问题

- 哪些任务适合串行、路由、并行或循环？
- 何时需要 Orchestrator-Worker？
- Evaluator-Optimizer 为什么可能无限循环？
- 如何组合多个模式而不让 Graph 失控？

### 内容结构

1. Prompt Chaining：拆分可验证阶段；
2. Routing：规则路由和模型路由；
3. Parallelization：独立子任务与多样本聚合；
4. Orchestrator-Worker：动态拆分未知数量任务；
5. Evaluator-Optimizer：生成、评价和修改闭环；
6. 每种模式的成本、延迟和失败特征；
7. 模式选择决策表；
8. 组合模式时的状态边界；
9. Multi-Agent 只是可能的实现方式，不是第六种万能模式。

### 案例演进

并行研究各章节，使用聚合节点合并资料，再通过评价—优化循环改进文章初稿。

### 读者带走

能够从任务依赖关系选择工作流模式，并为循环设置明确的退出标准。

## 第 10 篇｜Checkpoint、Thread 与 Memory：Agent 如何保存和恢复状态

### 核心命题

Checkpoint 解决运行状态的持久化与恢复，Memory 解决跨步骤或跨会话的信息保留；二者相关但不是同一个概念。

### 要解决的问题

- 上下文、历史消息、Checkpoint 和 Memory 有什么区别？
- Thread 标识的到底是什么？
- 进程退出后，Agent 如何从中断位置恢复？
- 长期记忆应该存什么，什么时候写入？

### 内容结构

1. 从“记住用户”和“记住执行到哪”两种需求切入；
2. Checkpoint 是状态快照，不是业务数据库；
3. Thread 是一次连续运行的身份边界；
4. 保存、恢复、重放和时间旅行；
5. 短期记忆与当前 Thread；
6. 长期记忆与跨 Thread Store；
7. 语义记忆、情景记忆和用户偏好；
8. 记忆写入、检索、更新和遗忘；
9. 并发、幂等性、隐私和数据生命周期；
10. 哪些数据仍然应该留在业务数据库。

### 案例演进

让研究助手保存文章任务，在服务重启后继续运行，并跨任务记住作者偏好但不复制全部对话。

### 读者带走

能够分别设计执行持久化和用户记忆，不再把“多存一些聊天记录”当作记忆方案。

## 第 11 篇｜Streaming、Interrupt 与 Human-in-the-loop

### 核心命题

流式交互不只是逐字显示答案，而是把一个长时间运行的 Agent 转换为可观察、可取消、可干预的事件系统。

### 要解决的问题

- Token、Message、State Update 和自定义进度事件有什么不同？
- 前端如何表示 Agent 的多阶段运行状态？
- Interrupt 如何暂停并恢复 Graph？
- 审批、修改和拒绝分别怎样影响后续执行？

### 内容结构

1. 为什么长任务不能只显示一个 Loading；
2. 内容流与运行事件流的区别；
3. Token、工具调用、节点更新和进度事件；
4. 将事件映射为前端状态机；
5. 取消、断线、重连、重复事件和最终一致性；
6. Interrupt 的暂停—保存—恢复模型；
7. Human-in-the-loop 不是弹出一个确认框；
8. 批准、编辑、拒绝与超时；
9. 敏感工具的审批策略；
10. 乐观 UI 为什么不适合不可逆操作。

### 案例演进

实时展示研究、写作和评价进度，在发布前暂停，由用户审阅大纲或最终文章后恢复执行。

### 读者带走

能够为 Agent 设计事件驱动 UI，并保证用户干预后状态仍然一致。

## 第 12 篇｜如何证明 Agent 真的能工作

### 核心命题

Agent 的可靠性不能通过几次演示证明，而要同时验证确定性组件、运行轨迹、最终结果、安全边界、成本和延迟。

### 要解决的问题

- 不确定输出如何测试？
- 应该评价最终答案还是执行过程？
- Trace 与传统日志有什么不同？
- Agent 上线需要哪些最低保障？

### 内容结构

1. Demo 成功为什么不能代表系统可靠；
2. 测试金字塔：函数、工具、节点、路由、Graph 和端到端；
3. 固定断言、规则型 Evaluator 与 LLM-as-Judge；
4. 数据集、回归测试和失败样本沉淀；
5. 结果评价与轨迹评价；
6. Trace：还原一次运行的父子调用、状态变化和耗时；
7. Token、延迟、工具次数和失败率预算；
8. Prompt Injection、越权工具和敏感数据测试；
9. 模型或 Prompt 变更如何灰度与回归；
10. 从 Demo 到生产的发布检查表。

### 案例收尾

## 11. 写作风格与统一规范

### 11.1 单篇文章结构

单篇建议控制在 3500～5500 字，并沿着同一条问题演进线展开：

```text
标题与首图
→ 约 100 字的引用式导读
→ 上一阶段的局限
→ 当前阶段是什么
→ 完整流程
→ 分步骤讲解
→ 引入的技术与常见方案
→ 本阶段解决的问题
→ 当前局限与下一阶段
```

导读统一写成一个引用段落，不设置独立标题：

```markdown
> **本文导读：** ……
```

从第二篇开始，导读之后先用 2～3 个短段落回顾上一篇的成果与局限，再进入本篇。第一篇则直接说明简单模型调用为什么会逐渐遇到问题。

### 11.2 内容写法

- 先讲业务问题，再引出技术，不直接堆叠术语或 API。
- 使用“AI 技术文章研究助手”贯穿全文，不频繁更换案例。
- 一篇只讲一个核心变化。每项新技术都要说明“用在哪里、为什么使用、解决什么问题”。
- 新名词第一次出现时写成 `English（中文解释）`；缩写尽量补充英文全称，例如“大语言模型（Large Language Model，LLM）”。
- 明确区分**核心能力**、**可选优化**和**工程配套**，不暗示使用的技术越多越好。
- 前文已经解释过的技术不再重复定义，只说明它在当前阶段发生了什么变化。
- 正文不设置“参考资料”章节；资料仍需在写作前根据第 10 节核对。

### 11.3 伪代码规则

- 使用简洁的 TypeScript 风格伪代码，不要求复制后直接运行。
- 每个关键步骤都添加中文注释，说明这一步的目的。
- 只展示主流程、状态、分支和终止条件，不展开框架 API 细节。
- 复杂流程优先使用短伪代码或表格解释，避免粘贴大段实现代码。

### 11.4 标题与排版

- 文章标题只使用一个一级标题 `#`。
- 主要章节使用二级标题 `##`。
- 完整流程中的“第一步、第二步”使用三级标题 `###`。
- 步骤内部的具体技术使用四级标题 `####`。
- 段落保持短小，一段只表达一个重点。

### 11.5 配图规则

- 图片按文章编号和出现顺序编号，例如“图 7-1、图 7-2”。
- 首图概括本篇新增的核心能力；流程图覆盖主要步骤、分支和结果。
- 图片必须帮助理解内容，不能只起装饰作用。
- 新图片统一使用 AI 生成的 PNG，不再新增 SVG 或 Mermaid。
- 流程图中的术语优先使用中文；需要保留英文术语时，采用“英文主标签 + 中文注释”的双语格式。
- 文件名使用 `文章编号-图片序号-内容说明.png`，例如 `07-01-workflow-overview.png`。
- 图片下方标注编号和一句简短说明，例如“图 7-1：并行研究与汇总流程”。

### 11.6 语言风格

- 简洁、直接、工程化，少用空泛总结和重复过渡。
- 用通俗语言解释复杂概念，同时保留必要的专业术语。
- 不使用绝对化表达；明确适用场景、成本、风险和取舍。
- 每篇结尾自然指出当前阶段仍未解决的问题，并引出下一篇。

正式发布前只检查五件事：核心命题是否清楚、术语是否解释、伪代码是否易懂、配图是否有效、文章是否自然推进到下一阶段。

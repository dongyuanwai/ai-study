## easy-23 · 什么是上下文工程（Context Engineering）？为什么说它是 2026 年最重要的 AI 工程技能？

- 难度：简单
- 原始分类：2. Prompt 与上下文工程（15 题）
- 资料类型：原始面试题

### 核心回答

上下文工程是围绕当前任务，决定模型在每一轮应该看到哪些信息，并管理这些信息的来源、选择、组织、更新和压缩。它覆盖系统规则、用户请求、历史、检索资料、工具定义、工具结果和任务状态。

Prompt Engineering 主要关注“如何表达指令”，上下文工程还要解决“信息从哪里来、什么时候加入、保留多久、哪些需要移出”。例如代码 Agent 应按需读取相关文件和测试结果，记录已做修改及待办事项，并把大段日志存到外部，只带回相关片段。

可以按六个动作理解：**获取、筛选、组织、维护状态、压缩、评测**。好的上下文需要相关、及时、有来源，并在有限预算中保留完成任务所需的证据。

题目中的“2026 年最重要”是趋势性表达，不能视为有客观排名的事实。它受到关注，是因为 Agent 和多轮工作流不断产生历史与工具数据，系统效果越来越依赖信息管理。实际工程中，它需要与评测、权限、检索和运行时设计共同发挥作用。

### 口述练习

上下文工程是管理模型每轮能看到的信息，包括指令、历史、资料、工具结果和任务状态。相比提示词工程，它还负责信息获取、选择、更新和压缩。随着 Agent 任务变长，这项能力直接影响成功率和成本；“最重要”可以理解为强调其价值，不能当成客观排名。

### 易错点

- 上下文工程不等于把更多材料塞进窗口。
- 记忆检索出的历史偏好也要检查是否已过期或与当前请求冲突。

## easy-24 · 什么是上下文压缩（Context Compaction）？有哪些常见的压缩策略？

- 难度：简单
- 原始分类：2. Prompt 与上下文工程（15 题）
- 资料类型：原始面试题

### 核心回答

上下文压缩是把较长的历史或资料转换成更短的可用状态，为后续交互腾出空间。目标是保留完成任务所需的信息，而不只是减少字数。它通常具有信息损失，需要关注压缩后的任务完成效果。

常见策略包括：

- **删除与裁剪**：移除重复消息、过期内容和无关日志，成本低但可能误删信息。
- **摘要**：把较早历史合并成短摘要，保留近期原文；适合长对话。
- **结构化状态**：记录目标、约束、用户选择、已完成步骤、失败尝试和待办事项；适合 Agent。
- **抽取式压缩**：保留与当前问题相关的原句，便于核对来源。
- **外部存储与按需检索**：将完整日志和文档保存在数据库或文件中，窗口里保留摘要、编号和访问路径。

部分平台也提供原生压缩机制。其返回状态可能是供模型续接的专用对象，并不等同于人类可读摘要；应按平台规范传递。[OpenAI Docs：Compaction](https://developers.openai.com/api/docs/guides/compaction)

实施时应保留当前指令、关键证据和未完成事项，记录来源，并在超出硬上限前触发压缩。

### 口述练习

上下文压缩是用更少 Token 保存任务继续执行所需的信息。常见方法有裁剪、历史摘要、结构化任务状态、关键句抽取和外部存储后按需检索。我会重点保留用户约束、关键证据和待办事项，再评测压缩是否影响后续任务，而不只看压缩率。

### 易错点

- 摘要可能把推测写成事实，应保存证据和不确定性。
- 压缩不会自动产生永久记忆，持久化需要应用实现。

## easy-25 · 当对话历史超出上下文窗口时，有哪些上下文压缩策略？各自的优缺点是什么？

- 难度：简单
- 原始分类：2. Prompt 与上下文工程（15 题）
- 资料类型：原始面试题
- 标签：AI、大模型、Agent

### 核心回答

应先判断哪些历史仍与当前任务有关，再选择保留策略。常见方法及取舍如下：

| 策略 | 优点 | 缺点与适用条件 |
| --- | --- | --- |
| 滑动窗口 | 简单、低延迟，保留最近对话 | 易丢失早期约束，适合短期关联任务 |
| 滚动摘要 | 历史连续，Token 可控 | 多次摘要会累积误差，应保留原记录 |
| 分层摘要 | 近期保留细节，远期保留概要 | 状态管理较复杂，适合长期任务 |
| 相关历史检索 | 按当前问题取回旧信息 | 可能漏检，需保存时间和来源 |
| 结构化状态 | 目标、约束和待办清晰 | 无法覆盖所有细节，适合流程型 Agent |
| 抽取关键原文 | 保留证据，减少改写误差 | 压缩率有限，适合关键决定和引用 |

工程上常用组合方案：**固定规则 + 任务状态 + 历史摘要 + 最近若干轮 + 按需检索**。近期消息也应受 Token 预算约束，而不能只按轮数保留。

如果历史已经超限，可以先在本地筛选、分段摘要或回溯到最近一次有效状态；不能把超限原文直接发给同一模型，期待它替自己压缩。处理工具消息时还应保证调用和结果关联完整，避免留下无法解释的孤立结果。

### 口述练习

滑动窗口快但容易忘记早期信息，摘要能保留全局但会损失细节，历史检索能按需取回信息但存在漏检。我通常组合固定规则、结构化状态、历史摘要和最近对话，再按需检索旧记录，并用 Token 预算控制总量。

### 易错点

- 不能简单删除最早消息，早期可能包含关键用户约束。
- 连续覆盖同一个摘要容易丢失事实，应保留可回溯原文。

## easy-26 · 什么是 Agent 的上下文窗口？为什么它是 Agent 工程中最核心的约束？

- 难度：简单
- 原始分类：2. Prompt 与上下文工程（15 题）
- 资料类型：原始面试题
- 标签：AI、大模型、Agent

### 核心回答

Agent 的上下文窗口本质上还是底层模型单次调用的 Token 范围。但 Agent 会循环执行“观察、决策、工具调用、接收结果”，因此历史和工具数据会不断增长。

一个 Agent 的窗口可能同时装入：行为规则、工具 Schema、当前目标、执行计划、用户消息、文件内容、工具结果和阶段状态。它们共同竞争有限空间，所以窗口约束会影响规划连续性、工具选择、任务成功率、延迟和成本。

例如代码 Agent 读取整个仓库再加入全部测试日志，容易挤掉用户要求和当前修改状态；更好的做法是先定位相关文件，分段读取，把完整日志保存到外部，只返回失败位置与必要片段。

工程上应实现：

1. 按类别设置 Token 预算，预留生成和工具返回空间。
2. 工具支持过滤、分页、字段选择和结果大小限制。
3. 将目标、约束、完成状态和待办事项显式记录。
4. 使用摘要、按需检索和子任务隔离控制信息增长。
5. 监控压缩后成功率，避免为了省 Token 丢失关键事实。

### 口述练习

Agent 的上下文窗口是它每次决策能看到的工作信息范围。由于 Agent 会不断产生工具结果和历史，这个空间很快被占满，进而影响规划连续性和执行质量。所以框架必须提供预算、工具结果裁剪、任务状态和压缩机制，而不能只依赖大窗口模型。

### 易错点

- 开更多工具会增加工具描述占用，也可能干扰选择。
- 子 Agent 结果仍会进入父 Agent 上下文，需要限制输出范围。

## easy-27 · （OpenClaw 前置知识）什么是 Agent 的 Context Window？为什么它是 Agent 工程中最核心的约束之一？

- 难度：简单
- 原始分类：2. Prompt 与上下文工程（15 题）
- 资料类型：原始面试题
- 标签：AI、OpenClaw、大模型应用开发、AI应用开发、Agent开发

### 核心回答

Context Window 可以理解为 Agent 本轮处理任务的临时工作台。模型本轮可直接访问的对话和外部资料，限于此次送入窗口的内容；它仍会使用参数中学到的知识。应用在磁盘或数据库中保存的资料，如果没有读取或检索进来，通常不会自动参与本轮判断。

以一个接收消息的 Agent 为例，窗口可能包括固定规则、用户新消息、最近对话、相关记忆、可用工具和刚查询到的业务数据。随着多轮工具执行，空间持续增长；如果压缩不当，Agent 可能忘记用户偏好、遗漏限制或重复已完成操作。

因此要分清三层：

- **长期存储**：完整历史、知识库、文件和业务数据。
- **任务状态**：当前目标、用户决定、已完成步骤和待办。
- **本轮窗口**：从前两者选出的必要信息，加上本轮输入。

这里是 Agent 的通用原理说明。面试涉及 OpenClaw 的具体实现时，还需结合对应版本的上下文装配流程解释。关键原则是“长期保存、按需读取、及时整理”，并保持证据和状态可追溯。

### 口述练习

Agent 的 Context Window 是模型本轮能使用的临时工作信息。应用保存了历史，不代表模型本轮已经看到了它。多轮任务中，需要把长期存储、任务状态和当前窗口分开管理，再按需加载相关内容，否则工具数据不断增长后，Agent 容易遗忘约束或重复操作。

### 易错点

- 保存历史和把历史传入模型是两个不同动作。
- 重要状态应由应用明确记录，不能只依靠模型从长对话中回忆。

## medium-9 · 当需要处理超长大模型上下文窗口限制时，有哪些可行的工程解决方案？

- 难度：中等
- 原始分类：2. Prompt 与上下文工程（21 题）
- 资料类型：原始面试题
- 标签：大模型

### 核心回答

先计算真实 Token 预算，给系统指令、用户输入、工具结果和输出预留空间。针对内容类型采用：检索只注入相关片段；长文分块并做分层摘要；历史对话保留最近轮次、重要事实和任务状态；工具结果截断、去重或存外部文件后按需读取；超长任务分阶段处理并保存中间产物。压缩后用关键事实核对或回源验证，防止摘要丢失约束。

### 口述练习

核心是选择性注入和分层压缩：检索相关片段、摘要旧历史、外置大工具结果，并为输出预留 Token。

### 易错点

大窗口不等于无限有效记忆；简单截断可能删掉决定性约束。

## medium-15 · 如何优化过长的提示词？提示词压缩有哪些技巧？

- 难度：中等
- 原始分类：2. Prompt 与上下文工程（21 题）
- 资料类型：原始面试题
- 标签：Prompt、提示词压缩

### 核心回答

先分析哪部分占 Token：重复规则、长历史、无关文档还是工具 Schema。删重复、合并同类约束、把静态说明模板化、检索相关片段、摘要旧会话、压缩表格和工具结果；不能压掉安全约束、输出契约和关键事实。用同一评测集比较压缩前后的准确率、拒答率和 Token，不要只追求字数最少。

### 口述练习

按 Token 占比定位冗余，再做去重、检索和分层摘要；压缩必须回归验证质量。

### 易错点

极短提示词可能更含糊，导致输出不稳定。

## concept-context-engineering · 上下文工程中的即时检索，如何与信息预加载配合？

- 难度：中等
- 原始分类：新概念研读
- 资料类型：补充研读
- 标签：Context Engineering、即时检索、上下文预算、信息选择
- 来源：[Effective context engineering for AI agents](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)
- 来源日期：2025-09-29；核对日期：2026-11-08

### 核心回答

即时检索先保留文件路径、查询或链接等轻量线索，在任务需要时再读具体内容。预加载则提前提供任务必需的规则和少量背景。

可以将稳定约束预加载，把大文件和动态资料留给工具按需获取，避免无关材料占满窗口。

### 口述练习

先给模型完成任务必需的规则，再让它根据线索寻找相关资料；不是把所有资料一次塞进去。

### 易错点

- 即时检索不是完全不提供初始上下文。
- 上下文窗口变大不意味着所有信息都值得保留。
- 这里记录工程文章日期，不宣称概念首次出现。

## 沟通原则

- 需求不明确时，及时追问，明确需求在开干
- 默认使用中文；代码、命令、变量名和文件名使用英文。
- 结论先行，直接进入正题；简单问题简短回答，复杂问题按需展开，不重复我已忽略过的建议。
- 给出真实判断；方案有问题直接指出，有更好的做法直接提出。
- 犯错时承认并修复；被纠正后仍有充分依据时应说明理由，不因一次纠正放弃原本正确的判断。
- 凡声称「已搜索」「已验证」或引用官方依据，必须完成有效查询、核对可信来源并提供来源；涉及可能变化的信息时查询当前一手来源，不凭记忆回答，无法核实时明确说明限制。
- 任务汇报保持简洁、专业，只保留关键结论、改动路径、验证结果、影响决策的必要逻辑和下一步；不输出完整 chain-of-thought。
- 回复中出现文件路径或 URL 等可点击文本时，使用完整绝对路径；路径后先加空格再接标点，避免终端将标点识别为路径的一部分。

## 执行与确认

- 明确指令即授权：用户已明确要求的操作，对象和范围清楚时直接执行，不重复确认，包括下述红线操作。仅在关键歧义、范围扩大或出现新的重大风险时确认。授权不延伸至用户未要求的独立操作，例如修改代码不代表授权提交、推送或部署。
- 已授权任务持续推进至验证和交付；等待回复时继续不依赖答案的工作。中途补充或纠正纳入当前任务，除非用户明确取消或替换目标。
- 因规则暂停时，说明具体文件、相关原文和适用原因，区分明确要求与自身推断。
- 提问、讨论、审查或规划时，只提供结论和方案；明确要求修改、实现、修复、执行或发布时，按授权范围实施。
- 对低风险、可逆且不影响结果方向的细节，说明假设后继续；涉及架构、数据、安全、外部写入或结果方向的关键歧义，必须先确认。
- 大改动或跨模块改动实施前，先说明计划、范围和验证方式；确认要求遵循「明确指令即授权」原则。
- 讨论或审查规范时只提供结论和方案，不自行修改；用户明确要求实施后，先修改规范文档，再按新规范执行后续改动。
- 修改项目文件、测试、构建、lint、类型检查、安装项目内依赖和调用只读外部接口等常规安全操作可以直接执行；遇到权限门禁时直接申请授权，只说明具体操作、修改位置和关键风险。
- 高风险操作遵循「红线操作」及专项规则，不得用宽泛的风险描述阻塞常规安全操作。
- 交付前检查结果与请求一致、必要验证已经完成、写作符合格式要求，并且没有触碰红线；无法完成或验证时，说明原因、未验证范围和阻塞项。

## Computer Use 与本地预览

- **工具选择**：优先使用专用 API、连接器、CLI 和系统原生命令；只有任务确实需要界面交互，且其他方式不适用时，才使用 Computer Use。
- **打开预览**：仅需打开本地文件、HTML 或 URL 时，macOS 默认使用 `open` 调用默认应用或浏览器；用户指定应用时遵循用户要求，不为打开预览启动 UI 自动化。
- **验证分离**：打开预览不等于完成验证。需要检查渲染、交互或截图时，按任务风险选择验证方式，不默认把简单预览升级为完整 UI 检查。
- **避免干扰**：使用 Computer Use 时优先新建任务标签页，不覆盖用户当前页面，不操作与任务无关的窗口。
- **阻塞处理**：遇到用户正在操作应用、权限拒绝或工具不可用时，不机械重试，不自行换应用触发新的授权。继续完成不依赖界面的工作，并说明未完成的验证。
- **如实汇报**：`open` 成功只代表已发起打开；只有实际检查页面后，才能声称显示正常或交互已验证。

## 项目文档体系

- 新项目先写 `AGENTS.md`；新目录先定结构约定。
- 项目级 `AGENTS.md` 规则可以覆盖普通全局偏好，但不得降低全局安全红线、公开发布限制和数据保护要求。
- 每次「更新文档」按照三份文档的规则和约束去对应更新。

### AGENTS.md 管理

- 项目级 `AGENTS.md` 应覆盖项目定位、核心目录及职责、工作流导航、文档指针、工程边界、执行纪律、验证入口和项目特有红线；不为套模板创建空章节。
- 只写长期稳定、经常使用、无法可靠推断或判断错误会影响结果的信息；新增规则前先合并同类内容，及时更新或删除失效规则，不重复全局规则和可通过文档指针引用的细节。

### README.md 维护

- 只描述项目当前真实状态；命令、示例和使用说明必须与实际一致，相关事实变化后同步更新。
- 详细文档由 `README.md` 或 `AGENTS.md` 提供入口，不在多处复制。

## 红线操作

以下操作须有明确授权，已授权时不重复确认；未授权时先确认，即使处于 auto-accept 模式。能够安全拆分时，可以先完成已授权的低风险部分：

- 删除文件或目录，或者覆盖、清空、回滚、重置用户数据与工作区；符合「临时文件与生成产物」规则的自动清理内容除外。
- 修改 `.env`、密钥、token、CI/CD、数据库 schema、迁移或生产数据。
- 安装全局依赖或修改系统配置；项目内依赖可以直接安装。
- 公开发布、生产部署、发送消息、发表评论或回复、创建或关闭 issue / PR、发布文章，以及其他会改变外部系统状态或被第三方看到的写操作。
- 执行 `reset`、`clean`、覆盖式 `restore` / `checkout`、rebase、改写历史、push、force-push、tag、release 及其他远端或高风险 Git 操作。
- 专项规则保留安全检查和操作限制；确认要求统一遵循「明确指令即授权」原则，系统和平台权限要求除外。

## 工程原则

### 代码审查与优化

- 执行新代码前先扫描一下，看看有没有病毒和高危代码，防止代码被投毒
- 代码审查、分析或“看看如何优化”等任务默认只读并止于报告；用户明确要求优化、重构、修复或按已确认方案修改时，可以在授权范围内实施。
- 重点检查正确性、安全、性能、兼容性、并发和测试缺口，以及实现是否简单直接、抽象是否必要、职责是否清晰、模块是否合理解耦分层、目录和依赖结构是否合理、命名是否准确简洁且易读。
- 检查死代码、重复实现和孤立文件；判断前必须核对静态引用、动态加载、配置入口、构建流程和运行时注册，证据不足时标记为「待确认」。
- 审查结果按严重程度列出问题、文件位置、判断依据、影响范围、建议方案和验证方式；未发现明确问题时如实说明，不为优化而制造改动。
- 实施优化时只处理授权事项并默认保持外部行为；声称获得性能提升时必须提供可复现的前后数据，完成后执行必要的回归验证。

### Bug 修复

- 修复 bug 时，优先稳定复现并定位根因，再实施最小修复，补充回归测试并验证失败路径和边界条件。
- 无法复现或同一方向连续两轮未解决时，停止猜测和试错，重新核对证据、搜索已知问题或对比正常版本；不得隐藏、绕过或弱化问题。


### 目标与验证

- 编码前明确可验证目标、改动范围、关键假设、验证方式，以及新增逻辑的无效输入、边界条件和期望结果；存在多种解释或实现路径时说明关键差异与权衡。
- 验证与改动风险匹配；相关检查及项目必需检查通过后交付，仅在新增改动、失败或具体疑点出现时扩大或重复检查。无法完成验证时说明范围和潜在影响。

### 实现原则

- 用最少且直接的代码解决当前问题，不添加需求范围外的功能，不为一次性或假设中的需求增加抽象、配置项、兼容层或复杂错误处理；存在明显更简单的实现时，优先采用。
- 优先使用标准库和项目已有依赖，不重复引入同类能力。
- 新增第三方依赖必须确有必要，并说明标准库和项目现有依赖为何不适用。进入生产运行链、影响安全边界、承载核心数据或难以替换的依赖视为核心依赖；引入前还应检查近期发布、维护状态、issue 响应和维护者活跃度。

### 外部接口调试

- 优先查找官方文档或可运行参考实现，包括 GitHub demo 和 SDK 源码。
- 逐字段对比 headers、body、参数生成逻辑和工具函数实现；「看起来差不多」不算完成对比。
- 禁止无证据归因；发现任务范围内的明确差异后，一次性修正再测试，避免让用户反复配合高成本操作。

### 修改边界

- 只修改任务直接相关的内容并遵循项目现有风格；修改前检查现有状态，不覆盖、回滚或整理用户的其他改动，不顺手重构、格式化、改注释或清理无关代码。
- 清理本次改动产生的孤儿导入、变量、函数和文件；预先存在的死代码只提醒，不擅自删除。文件删除遵循授权规则，符合临时文件与生成产物清理条件的除外。
- 默认精确检索和局部读取，修改文件优先使用清晰补丁；避免无关的大段日志、diff、输出和批量文本替换。

## Git 规则

- 新项目默认使用 `master`；已有项目遵循仓库当前默认分支和项目规范。仅当项目使用 `release` 分支时，`release` 只接收稳定版本。
- `add` 和 `commit` 仅在我明确要求提交时执行。每次 commit 前自动执行「更新文档」流程并完成必要验证，再将代码和受影响的文档一并提交；无需为未受影响的文档制造改动。
- Commit 信息使用中文，前缀使用 `init:`、`feat:`、`fix:`、`refactor:`、`docs:` 或 `chore:`；描述必须说明改了什么、原因和影响，禁止使用「修复 bug」「优化代码」「调整」等泛化表述，不添加 `Co-Authored-By`。
- 新项目的 `.gitignore` 至少排除依赖、构建产物、真实环境配置、系统文件、编辑器配置和 AI 本地配置；`.env.example`、`.env.*.example` 等不含密钥的配置模板应允许提交。

## 基础设施与部署

- 服务器和 Cloudflare 的只读检查可以直接执行；状态变更须先说明具体操作、涉及的配置或数据、关键风险、恢复方式及对其他项目的影响，确认要求遵循「明确指令即授权」原则。
- 授权覆盖多步操作时，可以按顺序连续执行并逐步验证；验证失败或出现新的重大风险时停止并报告。

# 项目开发约束

- 本地开发修改不代表发布授权；未经明确要求，不部署、不推送托管仓库、不绑定域名、不启用索引。
- 使用 loopback 地址预览，网站无需登录或账户。
- 保留中英文路由和 SEO 基础配置；本模板不含文章、分类或目录市场模块。
- 新项目使用自己的域名、统计 ID、IndexNow key 和托管绑定，不复用其他站点身份。
- 项目说明类 Markdown 和环境配置注释使用简洁中文；英文站文章保留英文，参数名、代码、路径和配置值不翻译。

## AI 学习模块

- 题目与答案由 scripts/import-questions.mjs 从 ../agent-docs 的原始 Markdown 和 ai-concepts-supplement.json 统一生成；新增联网研读内容维护在补充 JSON，保留来源、事件日期与核对日期，修改后重新导入，不手工维护生成题库。
- 题库原文为中文；保留中英文路由和界面。
- 页面与组件遵循已确认的白色简洁设计，导航集中展示首页、知识库、AI 时间线和能力测试。
- 默认 ALLOW_INDEXING=false；没有明确授权，不启用索引、统计或发布。
- 使用 Turbopack，不添加 --webpack 作为构建回退。
- Vercel 使用 Next.js 预设，Root Directory 为 code，输出目录保持自动识别；静态导出的 out 不是适配器读取清单的目录，禁止将 Vercel outputDirectory 设为 out。部署说明见 README.md。
- 界面文案精简：只保留帮助用户理解内容、状态或完成操作的信息；不擅自添加装饰性英文、空泛口号、重复宣传语或实现细节说明。
- 页面布局紧凑：header 与正文保持适度间距，不因窗口增高而拉伸主视觉、产生大块顶部留白；首页在常见 PC 尺寸下尽量一屏完整展示，不通过隐藏或裁切内容强行消除滚动。
- AI 时间线采用从 2023 年起的页面滚动驱动时间线，采用贯穿页面的中央纵向时间轴，知识节点按时间在左右两侧交错排列，滚动联动轴线进度、节点入场和全屏背景，并尊重减少动态效果偏好，知识点归入模型与推理、训练与对齐、检索与知识、智能体与应用四类，点击后展开详情。内容维护在 src/data/ai-timeline.json；新增节点须核对原始论文或官方公告，标明事件类型，避免将相关术语误记为同年诞生。

- 持续知识更新记录在 docs/knowledge-updates.json；只收录核实过的一手来源，按稳定 ID 和概念去重，使用 questionIds 关联新增时间线与题目。官方解读使用 article 类型，不伪装成概念首发；日期精度不足时保留 YYYY-MM，不编造日期。定时执行由应用任务管理，文档本身不负责调度。
